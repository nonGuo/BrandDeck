# 排版策略：为什么不"简陋"是模板的问题，以及怎么改

> 本文是改造方案，不是宣传材料。所有判断都附实测数据或代码位置，便于逐条反驳。
> 调研对象：[`example/ppt-master`](../example/ppt-master)（Claude 技能驱动，LLM 直接画 SVG）、
> [`example/presenton`](../example/presenton)（JSON 版式 + 浏览器渲染）。

## 0. 结论先行

**输出简陋不是模板造成的。** 华为模板本身有一套可用的视觉系统（4 张整版背景图、
脚注、Logo、7 个版式），而我们一个都没用——`compile.js` 用 `new PptxGenJS()` 起了一份
全新演示，自己 `defineSlideMaster` 画"纯色底 + Logo + 页脚 + 页码"，模板只贡献了
颜色 / 字体 / Logo 三个令牌。

用户提出的"和模板解耦、模板丰富就基于模板、模板简陋就降级用默认版式"，**方向对，
但需要修正一处**：模板的"丰富"其实是**两个独立维度**，混在一起判断会做错决定。
华为模板恰好是"视觉丰富、结构简陋"——如果只按一个"丰富度"分数判断，它会被判成
"丰富"，然后我们试图绑定内容版式却绑不到；判成"简陋"，又会把它的背景图白白丢掉。

## 1. 实测证据

### 1.1 我们当前产出（`demo/branddeck-intro-v3.pptx`，18 页）

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| 每页元素数 | 12（内容页） | 6 文本框 + 6 形状（红条 + 5 个圆点标记） |
| 画布覆盖率 | **0%** | 没有任何元素覆盖背景；每页 `background: #FFFFFF` |
| 背景 | 纯白 | 全篇同一底色 |
| 装饰 | 无 | 除标题下的红条与列表圆点外无其它图形 |
| 页脚 | 一行文字 + 页码 | 由我们自己的母版画 |

### 1.2 华为模板实际拥有（`PPT模板-HW.pptx`）

| 母版 | 版式 | 关键几何（英寸） |
| --- | --- | --- |
| 1 | 探索 / 智能 / 攀登 / 灯塔 | 整版背景图 13.34×6.13；装饰形状 0.77×0.79；标题占位符 `(0.98, 0.99) 7.17×0.75`；正文 `(1.02, 2.13) 7.15×0.70` |
| 2 | 1_Contents page | 正文占位符 `(1.13, 2.02) 11.07×3.30`；"目录"文本框 + 线条 |
| 3 | 1_Chinese text page | 标题 `(0.80, 0.50) 11.75×1.09`；正文 `(0.81, 1.64) 11.74×5.13` |
| 4 | End page | "Thank you." 文本框 `(0.66, 1.53) 4.29×0.93` |

母版级还有：`Security Level:` 占位符（`(0.99, 6.86)`）、`Huawei Confidential` 文本框、
HUAWEI Logo 图片（`(10.07, 6.54) 2.47×0.53`）。

`layouts.json` 的 media 清单已经把**背景图与版式的对应关系**记下来了：

```
ppt/media/image2.png  1949×917  referencedBy: slideLayouts/_rels/slideLayout1.xml.rels
ppt/media/image3.jpeg 1949×917  referencedBy: slideLayout2
ppt/media/image4.jpg  1949×1122 referencedBy: slideLayout3
ppt/media/image5.jpeg 2982×1657 referencedBy: slideLayout4
```

即"哪个版式用哪张背景图"是已知数据，只是没被读取。

### 1.3 模板"结构"维度的真实贫乏

按占位符签名统计 7 个版式：

| 占位符组合 | 数量 | 能承载什么 |
| --- | --- | --- |
| `CENTER_TITLE + BODY` | 4 | 封面式标题 + 一段正文 |
| `BODY` | 1 | 目录 |
| `SUBTITLE + OBJECT` | 1 | 中文正文页 |
| `(none)` | 1 | 结束页 |

**没有任何双栏 / 图文 / 图表 / 引用 / 指标版式。** 所以"完全基于模板生成内容页"这件事，
在这个模板上做不到——不是我们偷懒，是模板没提供槽位。

### 1.4 我们的几何是自定的，不是模板给的

`schema.js` 的 `SAFE_AREA` 是四边 64px（0.67in）；模板正文页的实际左边距是 0.81in、
标题顶边 0.50in。差异不大，但说明"内容框"从来不是从模板推出来的——这正好是可以改的地方。

## 2. 两个参考项目的做法

| 维度 | ppt-master | presenton | 我们（现状） |
| --- | --- | --- | --- |
| 模板载体 | 目录 + 每版式一个**完整页 SVG 原型**（带 `data-pptx-*` 结构元数据） | 单个 `template.json`：1280×720 绝对定位元素树（9–34 版式/包，共 383） | `.pptx` → 令牌 + `layouts.json`（几何） |
| 版式选择 | **LLM**（Strategist）从枚举清单里选，写进 schema 校验的 `spec_lock.md` | **LLM** 选版式下标；越界兜底是 `random.randrange()` | **确定性规则**（`inferKind`）+ 作者显式 `版式：` |
| 几何归属 | **LLM 手写绝对 px**，没有排版引擎 | 元素绝对 px + flex/grid **流式求解器**（JS/Python 各一份） | 确定性生成器算好绝对 px |
| 溢出处理 | 不缩字不截断，靠检查器 1px/5% 门禁 + 回推上游 | **无运行时测量**，靠写作期预算 `maxLength`，溢出直接裁掉 | 字号阶梯 + 超量进备注 + `repairDeck` 告警 |
| 模板丰富度判断 | **没有**，明说"模板大小是证据不是策略"；降级靠 reuse ladder（mirror→layout→style→free） | **没有**，只有 Standard / Smart 两种生成模式 | 没有 |
| 主题提取 | 架构上分离（Brand 只管色/字/logo，Layout 禁止染指） | 面积加权聚类出 16 色 + 确定性兜底；Logo **不单独提取**（烤进版式当装饰） | 已提取色/字/Logo 三令牌 |
| 最终渲染 | 自研 DrawingML writer（原生 pptx，1 SVG px = 9525 EMU） | HTML → Chromium → **外部预编译包** `@presenton/export-core` | pptxgenjs（原生 pptx） |
| 观感来源 | 排版纪律：5 个间距锚点、4 级字号 ±2px、60-30-10、节律标签、≤3 阴影、scrim 渐变 | 装饰语法：命名装饰层、图片 `focus_x/y`+`clip_path`、27 种信息图组件、字数预算、反裁切 linter | 弱：红条 + 圆点 + 分栏 |

## 3. 修正后的判断模型：两个维度，四种情况

```
视觉维度（skin）：背景图 / 装饰形状 / 脚注 / Logo 位置 / 母版级图形
结构维度（frame）：可承载内容类型的版式集合（正文/双栏/图文/图表/指标/引用…）
```

|  | 结构丰富 | 结构贫乏 |
| --- | --- | --- |
| **视觉丰富** | **A. 全绑定**：内容装进模板版式，视觉沿用模板 | **B. 皮肤 + 自有版式**（华为案例）：背景/脚注/Logo 照搬，内容版式用我们的库 |
| **视觉贫乏** | **C. 结构 + 自有皮肤**：版式借模板的槽位，皮肤用令牌推出来的极简风 | **D. 全兜底**：今天的默认行为 + 令牌 |

判定（对每个模板解析一次，结果落进 `theme.json`）：

- `visualScore`：背景图数（每张 +3）、装饰形状数（+1）、母版脚注文本（+2）、独立 Logo（+2）；
  `>= 4` 判视觉丰富。
- `structuralScore`：**互不相同的占位符签名数**。`>= 4` 且包含至少一种"内容型"签名
  （BODY 之外的 OBJECT/CHART/TABLE/PICTURE 组合）判结构丰富。华为得 4 种签名但只有
  `SUBTITLE+OBJECT` 一个内容型 → 判"结构贫乏"。

> 用户原话是"模板简陋就降级"。上面的修正只是把"简陋"拆成两个可测的量——结论仍是
> 用户的方向：**模板只提供它真正有的东西，缺的部分由我们兜底**，只是"缺"要分类。

## 4. 改造方案

### P1 皮肤层：把模板的视觉系统用起来（收益最大、改动最小）

1. `template.js` 在解析时导出背景图：按 `media.referencedBy` 把 `slideLayoutN` 的背景图
   落到 `<dataDir>/templates/<id>/backgrounds/layout-N.<ext>`，并把
   `{layoutPart, name, path, widthPx, heightPx}` 写进 `theme.json` 的 `brandAssets.backgrounds`。
2. `theme.js` 增加"版式背景图"识别：布局里**铺满画布**的 `PICTURE`（面积 ≥ 画布 85%）
   即视为背景图，而不是普通图片。
3. `compile.js` 的 `defineMaster` 支持 `background: { path }`，并按 `variant` 注册多个母版
   （封面 / 内容 / 目录 / 结束），内容页母版挂母版脚注（`Security Level:`、
   `Confidential`）——这些文本从模板母版读，读不到就用配置项。
4. 生成器按页型选母版：`cover`→封面母版、`section`/`toc`→目录母版、正文→内容母版、
   封底→结束母版。

验收：同一份材料重新出片，内容页背景与华为模板一致（视觉不再是纯白），
`pptx` 里母版背景是**图片**而非纯色；`test/engine-compile.mjs` 增加"母版背景图存在"的断言。

### P2 内容框来自模板，而不是我们的 64px

1. 解析时取"内容型版式"的 `BODY` 占位符几何，换算成 px 写进 `theme.json`
   （`frame: { x, y, w, h }`），并保留 `SAFE_AREA` 作为兜底。
2. `generate.js` 的 `innerBox(theme)` 优先用 `theme.frame`；版式常量（标题带高度、
   内容区起始 y）改为相对该框计算，而不是硬编码 64/172。
3. 若模板没有内容型版式 → 用默认框（现行为）。

验收：华为模板下标题落点 ≈ `(0.80, 0.50)`in 而非 `(0.67, 0.67)`in；
`test/generate-test.mjs` 增加"内容框随主题变化"的断言。

### P3 版式库升级：从两个项目借具体机制

按性价比排序，逐条独立可验收：

| # | 机制 | 来源 | 我们怎么落 |
| --- | --- | --- | --- |
| 1 | **几何推导的字数预算**（`maxLength = 宽/字宽 × 行数 × 0.85`） | presenton | 现有 `slideCharBudget` 是全局值；改成**按槽位**算：标题槽/要点槽/卡片槽各有预算，供提示词使用 |
| 2 | **`decorative` 布尔契约** | presenton | 元素级加 `decorative?: true`，装饰不参与字数统计/不参与"薄页"判定/不被 refit 改动 |
| 3 | **重复容器的 min/max children** | presenton | 卡片/时间线节点做成"3 张卡与 2 张卡共用一套版式"，而不是各写一个 builder |
| 4 | **节律标签（anchor / dense / breathing）** | ppt-master | 现在的 `breather` 是隐式插入；改成每页显式标节律，并加"密集页后必须跟呼吸页"的检查 |
| 5 | **5 个间距锚点 + 4 级字号 ±2px 容差** | ppt-master | 收进 `style`（`anchors: {margin, blockGap, gutter, radius, leading}`），并把"字号只能取阶梯值"做成断言 |
| 6 | **机械重叠/溢出闸门（1px / 5%）** | ppt-master | `repairDeck` 现在是告警；把"重叠 > 1px"和"文本溢出 > 5%"升级为**硬失败**，可配置 |
| 7 | **60-30-10 配色比例 + 每页 ≤3 阴影 + 一个容器只用一种"重量"工具** | ppt-master | 写进 `TONES` 的生成规则，并用 `test/api-test` 断言颜色用量 |
| 8 | **版式菜单式提示词**（列出枚举 + 一句描述，让模型选） | 两者 | 现在的 `版式：` 是自由文本 + 别名表；改成提示词里给出**当前可用版式清单**（受模板结构限制后的子集） |
| 9 | **图片 `focus_x/y` + `clip_path`** | presenton | DSL 的 `image` 元素加 `crop` 字段，编译成 pptx 的 `crop` 参数（pptxgenjs 支持 `sizing.crop`） |

明确**不照搬**：

- ppt-master 的"LLM 手写绝对坐标"：它靠 422KB 检查器 + 内嵌字体度量表兜底，
  与我们"确定性出几何"的取舍相反；照搬会丢掉一致性与可复现性。
- presenton 的"无运行时测量、溢出裁掉"：我们有更好的处理（进备注）。
- presenton 的"越界随机选版式"：宁可用结构化兜底（降级为列表）。
- HTML→PPTX 渲染：与"原生可编辑"的产品前提冲突（图表会变图片）。

## 5. 落地顺序建议

1. **P1 皮肤层**（1 个改动单元）：立刻消除"纯白页"，观感提升最大。
2. **P3-4/5/6 排版纪律**（3 个小单元）：让页面"像设计过"的第二层，不依赖模板。
3. **P2 内容框**：让几何跟着模板走，避免"皮肤是华为、骨架是通用"的割裂感。
4. **P3-1/2/3**：预算与容器抽象，属于结构性重构，放在视觉稳定之后。
5. **A 档（结构也丰富的模板）全绑定**：只在拿到真正有内容型版式的模板时再做，
   避免为不存在的能力写代码。

## 6. 已消除的风险：图片背景（已实测）

P1 的技术前提已用 spike 验证通过（`pptxgenjs` 生成 + LibreOffice 渲染 + 解包查 XML）：

| 问题 | 实测结果 |
| --- | --- |
| pptxgenjs 能否给母版/版式设图片背景 | 能：`defineSlideMaster({ background: { path } })` |
| 存成什么结构 | **版式级 `<p:bg><p:bgPr><a:blipFill r:embed=…>`**（`ppt/slideLayouts/slideLayout2.xml`），图片落在 `ppt/media/` |
| 渲染是否一致 | 是：LibreOffice 整页背景正确（红底白字实测） |
| 与华为模板是否同类机制 | **同类**：模板也在各 `slideLayoutN` 的 rel 里挂背景图，一一对应 |

结论：P1 不是"用形状模拟背景"，而是**生成与模板同构的 layout 背景**。

## 7. 其余风险与待验证

- **背景图与内容框的视觉冲突**：模板背景图铺满 13.34×6.13in，我们的内容框是 0.67in 边距。
  P1 落地后需逐页核对，必要时按背景的视觉留白调整内容框（而非裁背景）。
- **母版脚注的合规语义**：`Security Level:` 是华为内部要求，通用模板没有。
  实现为"模板有就继承、没有走配置项、配置为空则省略"，不硬编码。
- **一个模板多套视觉**：模板有 4 套主题版式（探索/智能/攀登/灯塔），需决定选哪套
  （配置项 + 默认第一套），否则封面与内容页可能不属于同一主题。
