# BrandDeck：把企业模板变成可编辑演示的工程实现

BrandDeck 是一个装在 DeepSeek Harness 里的插件，解决一个具体问题：企业里做一份合规的演示文稿，平均要花 5 天，其中大部分时间不是花在内容上，而是花在"找模板、对齐品牌色、调字体、修版式溢出"上。BrandDeck 把这条链路上的机械劳动自动化，同时保证产出的 `.pptx` 是**原生可编辑**的——业务方拿到文件后可以像普通 PPT 一样改字、改图、改配色，而不是拿到一堆截图。

## 一、为什么不用"直接生成 PPT"

市面上多数 AI 生成 PPT 的做法，是让模型直接产出排好版的成品，或者干脆把整页渲染成图片塞进幻灯片。这两条路都有硬伤。

第一种做法的问题是不可控。模型不知道你的画布是 1280×720，不知道安全边距是 64 像素，不知道右上角要给 Logo 留 150×48 的位置，于是经常出现标题压住 Logo、正文溢出画布、两个元素叠在一起。这类错误在生成时看不出来，打开 PPT 才发现，返工成本比手做还高。

第二种做法的问题是不可编辑。图片嵌进 PPT 就是一整块像素，业务方想改一个错别字都不行，只能回来重新生成。这在真实交付里是不可接受的，因为评审会上一定会有人要求改字。

BrandDeck 的取舍是：**内容与版式解耦**。模型只负责产出结构化内容（一份卡片 DSL），版式计算由确定性代码负责。模型再离谱，也不可能产出越界或重叠的卡片，因为它根本碰不到坐标计算。

## 二、整体架构：四层流水线

整条链路分成四层，每层只做一件事，层与层之间用数据契约连接。

第一层是模板特征提取。输入是企业提供的 `.pptx` 模板文件，输出是一组设计令牌：品牌色板、中英文字体、母版 Logo。这一层只在管理员上传或更新模板时执行一次，解析结果落盘保存，之后所有卡组复用同一份令牌。

第二层是内容生成。输入是用户的文字材料或一句话描述，输出是结构化的卡片 DSL。这一层是纯文本模型的工作，但它写出的东西必须通过 Zod 强校验。

第三层是可视化微调。输入是卡片 DSL，输出仍是卡片 DSL，只是被人在 16:9 画布上手动调整过位置、字号、文案。这一层是给人用的。

第四层是原生编译。输入是卡片 DSL 加设计令牌，输出是 `.pptx` 文件。文本变原生文本框、图形变原生形状、图表变 Office 图表、SVG 示意图按 3 倍分辨率光栅化后嵌入。

## 三、模板解析：真实模板里的坑

这一层看起来最简单，实际上最容易踩坑。以用来验证的华为模板为例，一个朴素的解析器会在至少四个地方出错。

第一个坑是主题色反转。这个模板的 `clrScheme` 里，`dk1`（深色一号）和 `lt1`（浅色一号）居然都是 `#1D1D1A`，而 `dk2` 和 `lt2` 都是 `#FFFFFF`。如果按"背景色取 lt1"的常规逻辑，解析出来的背景会是近黑色，整份演示直接废掉。真实的白底来自母版上显式的 `<p:bg>` 填充，而不是主题色槽。所以正确的做法是：优先读母版的实际背景填充，主题色槽只作为兜底，并且当发现 `lt1 == dk1` 时要报警。

第二个坑是页面尺寸不标准。这个模板的 `sldSz` 是 `cx=12196763`、`cy=6858000`，比标准的 16:9（12192000×6858000）宽了 4763 EMU。硬编码 12192000 会导致所有元素右移，Logo 被切掉一角。必须老老实实读 `sldSz`，再把它映射到 1280×720 的虚拟画布上。

第三个坑是 Logo 的位置。多数模板把 Logo 放右上角，这个模板放在右下角，坐标是 x=10.07 英寸、y=6.54 英寸。更麻烦的是，这个 Logo 图片同时被母版 1 和母版 4 引用，所以"只被一个母版引用的图片才是 Logo"这种启发式判断会失败。正确的判据是：被母版（任意数量）引用、且不被版式或幻灯片引用、且宽高比在 1.5 到 8 之间、且像素尺寸不大。

第四个坑是字体。这个模板的 `<a:ea>`（东亚字体）是空字符串，不是缺失属性。如果直接取 `ea` 字段，会得到空字体名。真实的中文字体藏在母版的 `txStyles` 里（标题是微软雅黑），或者是 `fontScheme` 里的 `<a:font script="Hans">` 映射。解析器必须按"母版 txStyles → 主题 ea → Hans 映射 → 拉丁字体"的顺序逐级回退。

处理完这四个坑，模板被格式化成四份可复用产物：`theme.json` 存设计令牌，`layouts.json` 存版式几何清单，`template.md` 存人类可读的品牌规格书，`source.pptx` 存原件副本。下次生成卡组时只需要引用 `templateId`，不再需要原始模板文件。

## 四、卡片 DSL：让模型在安全区内自由排版

卡片 DSL 是一个 JSON 结构，画布坐标固定为 1280×720。一页卡片包含若干元素，元素类型有五种：文本、图形、图表、SVG 示意图、图片。

文本元素有语义角色，分标题、副标题、正文、注释四级。颜色不写死，而是写令牌引用，比如 `$colors.primary`。这样同一个卡组换模板时，颜色会自动跟着变。

图形元素支持矩形、圆角矩形、椭圆、直线、右箭头五种。图表支持柱状、折线、饼图三种，数据是标签数组加序列数组。SVG 元素装载模型手写的矢量代码。图片元素通过 `assetKey` 引用品牌素材库。

DSL 之上有一层修复逻辑，在保存前一定会跑。它做五件事：把越界的坐标钳制回画布内；把压到 Logo 角落的文字往下推；给太小的文本框一个最小尺寸；把重复的元素 id 改名；把 SVG 里不允许的标签（`foreignObject`、`script`）剥掉。每一处修改都会写成一条告警返回给调用方，让人知道发生了什么。

还有一条信息密度约束：单页正文总量不超过 150 字。超出会告警。这条规则来自一个朴素观察——一页超过 150 字的演示，观众读不完，演讲者也只能念稿。

## 五、版式路由：按内容形状选版式

早期版本所有内容页都是同一种"要点列表"，结果整份演示看起来像同一页复制粘贴。后来引入了版式路由：按数据的形状选版式。

两条并列关系用双栏对比。三条并列用横向三列。四条用 2×2 网格。以数字为主的用指标卡。有时间顺序的用横向时间线。单条内容字数多（超过 35 字）自动降级为通栏列表，因为塞进小卡片会溢出。

版式可以由模型在大纲里显式声明，比如在页面标题下面写一行 `版式：对比`；也可以由代码根据内容自动推断。推断规则保守：出现"对比、相比、旧、新"这类线索才判为对比；出现两个以上带单位的数字才判为指标；出现"第一步、阶段、Q1"这类有序线索才判为时间线。显式声明优先，推断绝不覆盖显式。

有一个刻意的克制：不做"为了不一样而不一样"的轮换。曾经实现过"连续三页同版式就把列表改成两栏对比"，测试立刻暴露问题——对比版式会把"现状：庚"拆成栏标题加条目，等于改写了用户的原话。宁可两页长得像，也不改语义。

## 六、SVG 示意图：先换肤，再嵌入

模型画的示意图会自带配色。常见情况是 Mermaid 的默认紫配绿，或者随机的渐变，标签字体是 Comic Sans。这些东西直接放进一个华为红的品牌卡组里，一眼就能看出是"贴上去的"。

所以 SVG 在光栅化之前要过一遍主题归一化：扫描所有 `fill`、`stroke`、`stop-color`，把饱和色映射到模板主色，把浅色映射到容器色，把深色映射到主文字色，把灰阶中间调映射到次要文字色；同时强制所有文本使用模板字体。`none`、`transparent`、`url(#渐变)` 这类语义值不动，几何结构也不动。

这里有一处判断需要说明。第一版实现是"不同原色映射到不同品牌色"，结果一张流程图里三个本应同色的流程节点被涂成红、品红、金三种颜色，凭空造出了不存在的层级。后来改成"同语义同色"：默认所有饱和色都落到品牌主色，只有显式声明 `distinctAccents` 的多系列图表才走模板图表色板。

## 七、长材料：Map-Reduce 分层提炼

一句话描述和一篇文章，不能用同一条路径处理。

单次提示词只能看到有限的上下文窗口；即使塞得进去，两万字的报告也会让模型质量显著下降——它会抓住开头的几节反复展开，后面的内容草草带过。所以超过 6000 字的材料走 Map-Reduce。

Map 阶段把材料按 Markdown 标题切成块，块与块之间不跨章节。每块单独提炼 3 到 8 条"可上页的事实"，要求保留原始人名、工具名、具体数字、时间节点，禁止使用"赋能、抓手、闭环、矩阵"这类空话。块大小目标是 4000 字，切分优先在段落边界，段落过长再在句末标点切，绝不丢字。

Reduce 阶段把各块的事实合并——去重按规范化文本相等判断，保守处理，因为两条看起来相似的事实往往带着不同的数字，而那些数字恰恰不能丢——然后一次性要求模型把这些事实编排成大纲：去重、聚类、排页、给每页起一个带结论的标题。

并发受控：最多 3 个 Map 调用同时进行。一份 12 块的材料开 12 个并发调用，既容易触发限流，出错时也很难定位是哪一块的问题。

## 八、两种可编辑的中间产物

生成很少一次到位。用户看完卡片视图，通常会说"第二页那句太长""这个对比放反了"。如果每次调整都要重跑整个生成流程，体验会很差。

所以每份卡组以目录形式保存两套真相。`card.json` 是几何真相，记录每个元素的位置、尺寸、样式、内容，是渲染和导出唯一依赖的东西。`outline.md` 是文字真相，是一份可读可编辑的 Markdown 大纲，每个元素用 `{#id}` 锚点标识。

改文字时，人只需要编辑 `outline.md`，保存后系统按 id 把内容写回对应的元素，位置和样式一字不动。新增一个 `### 正文 {#新id}` 段落会自动排版进安全区，不压到已有文字上。删掉某一段默认不删元素，需要显式指定才删除——避免误删。

每次保存都会留一份修订快照，默认保留最近 20 版，可以回溯。

## 九、会话入口：/branddeck

对话式的生成能力做成了会话命令，而不是面板里的一个角落。在对话框输入 `/branddeck` 就能看到用法和当前状态。

`/branddeck deck <一句话描述>` 生成卡组。`/branddeck file <路径>` 从长材料文件生成。`/branddeck style <一句话描述>` 把描述翻译成一份可复用的风格配置并保存。`/branddeck list` 和 `/branddeck templates` 查看已有卡组与模板。

命令的执行结果直接写进会话记录：生成了哪个卡组、多少页、用了哪个风格、下一步该敲什么命令。实测一句话"对比自建模板与统一模板库，再讲三步落地"能产出 10 页卡组，包含双栏对比页和时间线页。

底层走的是 Host 侧的模型调用，用的是当前会话的模型选择。版面仍然由确定性生成器负责，所以模型输出的质量波动只影响内容，不影响排版正确性。

## 十、验证：不靠"应该能用"

这个项目从一开始就坚持一件事：不写没有跑过的结论。

自动化测试分 16 套，覆盖依赖可用性、中文渲染、DSL 契约、模板解析、存储、光栅化、编译、版式、节奏、SVG 换肤、命令、客户端静态审计、HTTP 传输、卡组包、端到端、长材料分块。合计两百多项断言，全部可复现。

模板解析的结果会和一份独立分析产物逐字段比对，28 个字段包括每一个原始色槽的取值。导出的 `.pptx` 会被 LibreOffice 渲染成图片，人工逐页核对：中文字有没有重影、Logo 在不在位、有没有元素溢出画布、图表是不是原生对象。

这套验证抓到过两个只在真实渲染里才暴露的缺陷。一个是中文重影：pptxgenjs 把同一个字体名同时写进 `<a:latin>` 和 `<a:ea>`，而 Arial 没有中文字形，渲染器回退时把中文画了两遍。修法是导出后处理，让东亚字体槽使用模板里的中文字体。另一个是启动崩溃：客户端插件把 `connection` 服务写进了硬依赖，而那个服务装在内置插件的私有作用域里，兄弟插件看不到，导致条目永久 pending、整个 web boot 失败。修法是去掉这个依赖，数据改走同源 HTTP 路由。

## 十一、已知边界

第一，面板里不能直接对话。对话能力做成了会话命令，因为 bundle 客户端插件看不到内置插件的连接服务。这是平台约束，不是取舍。

第二，SVG 按设计文档要求以位图嵌入，所以示意图在 PowerPoint 里不可再编辑。文本、图形、图表都是原生对象，只有示意图是图片。

第三，导出依赖本机字体。容器部署时需要通过配置显式挂载中文字体文件并关闭系统字体加载，否则中文会变成方块。

第四，卡组存储是工作区无关的全局存储，多个会话共享同一批卡组。需要按项目隔离时，配置不同的数据目录即可。

## 十二、设计取舍：几个被否掉的方案

做这个项目的过程里，有几个方案看起来更省事，但都被否掉了，理由值得记下来。

第一个被否掉的是"用 python-pptx 直接拼 PPT"。这条路的好处是生态成熟、文档齐全。问题在于它运行在 Python 里，而插件本身是 TypeScript/JavaScript。跨语言调用意味着要维护一个 Python 运行时、处理编码与路径差异、在容器里装依赖。更麻烦的是类型不同源——DSL 是 TS 定义的，导出器是 Python 写的，两边字段名一旦漂移，报错会发生在运行时的深处。所以最后选了 pptxgenjs，全栈同源，一个 Zod schema 管住两端。

第二个被否掉的是"直接嵌入 SVG 而不光栅化"。PowerPoint 2016 以后确实支持 SVG 图片，看起来可以省掉光栅化这一步，还能保持矢量清晰度。但这个支持在不同版本、不同平台（Windows、macOS、Web 版、WPS）的表现并不一致，实测有版本会把 SVG 显示成空白。设计文档里明确要求规避这个风险，所以最终选择按 3 倍分辨率光栅化成 PNG 再嵌入——牺牲了可编辑性，换来跨版本稳定。

第三个被否掉的是"让模型直接写坐标"。最初想让模型输出每个元素的绝对位置，省掉版式计算。实测下来这是灾难：模型对小数的空间感很差，同一个版式每次生成的坐标都不一样，元素经常叠在一起或跑出画布。改成"模型只给内容、代码算位置"之后，越界和重叠问题直接消失。

第四个被考虑后放弃的是"自己做前端打包"。DSH 的客户端插件支持单文件纯 JS 模块，用 `window.__ModuleLoader__.load` 注册。一开始觉得这限制太死，想引入 Vite 打包成 bundle。但引入构建链意味着插件安装时要跑构建、要处理依赖版本、要考虑 HMR 与产物缓存。单文件方案虽然写起来啰嗦，但安装即用，没有构建步骤，也没有构建失败的排查成本。

## 十三、数据结构：三层契约

整个系统靠三层数据结构串起来，每层都有自己的校验。

最底层是设计令牌 `ThemeTokens`。它描述一份模板"长什么样"：背景色、容器色、主文字色、次要文字色、品牌主色、强调色、图表色板数组；标题字体、正文字体、拉丁字体；以及品牌素材（Logo 路径、像素尺寸、在母版上的真实摆放坐标、图标字典）。令牌是唯一允许出现硬编码颜色的地方，其他所有层的颜色都必须是令牌引用。

中间层是卡片 DSL `CardDeck`。它描述"这份演示讲什么、怎么排"：卡组 id、标题、引用的模板 id、若干页；每页有页面 id、版式意图、背景、演讲备注、若干元素。元素按类型分为文本、图形、图表、SVG、图片五支，每支有自己的必填字段。这一层是模型唯一直接书写的结构。

最上层是编译入参。它是 DSL 加令牌加 Logo 字节加素材字典，加上一组编译选项（SVG 光栅化倍数、字体文件、是否加载系统字体、页脚文案、页码开关）。这一层不对外暴露，是编译器内部约定。

三层都过 Zod。令牌用 `ThemeTokensSchema`，卡组用 `CardDeckSchema`，元素用 `SlideElementSchema`（判别联合，按 `type` 字段分流）。校验失败不会抛异常给用户，而是返回结构化的 `issues` 数组，每条带路径和原因，这样模型能看懂错在哪、用户也能看懂。

## 十四、失败处理：三处刻意的降级

系统里有三处刻意设计的降级，目的是"局部失败不影响整体"。

第一处是模板规格书生成。解析模板时会顺带生成 `layouts.json` 和 `template.md`。这两个产物是锦上添花，不是核心。所以这一步用惰性导入并且包了 try/catch：如果生成器模块缺失或抛错，只把错误记进 `meta.specError`，令牌照常落盘。这个设计来自一次真实事故——早期版本把规格书生成写成静态导入，结果模块没就绪时整个插件加载失败，所有 API 返回 405，排查花了很久。

第二处是 SVG 光栅化。一张示意图渲染失败不应该让整份演示导出失败。所以单个 SVG 元素失败时只记一条告警并跳过该元素，其余元素照常写入。用户会看到"第 3 页的示意图未能渲染"，但文件本身是可用的。

第三处是图标素材解析。DSL 里的图片元素通过 `assetKey` 引用素材，而素材可能已被删除。找不到时同样只告警跳过，不中断导出。

## 十五、性能：几个实测数字

解析一份 2.3 MB 的企业模板，耗时约 300 毫秒，其中解包 ZIP 和解析 XML 占大头，图片尺寸嗅探几乎不耗时。

编译一份 6 页的演示，200 毫秒到 900 毫秒，取决于有没有 SVG。SVG 光栅化是主要成本——一张 1100×250 的示意图按 3 倍分辨率渲染，约 300 毫秒。

一次完整生成（一句话到 6 页卡组），模型调用约 5 到 15 秒，其余环节可以忽略。这也说明瓶颈完全在模型侧，本地计算不是问题。

长材料走 Map-Reduce 时，调用次数等于块数加一。一份 12000 字的材料按 4000 字分块是 3 块，加一次 reduce，共 4 次调用；并发上限 3，所以实际耗时约等于两轮往返。

## 十六、结语：这套东西适合什么场景

BrandDeck 适合"高频、有固定品牌规范、内容需要反复修改"的演示场景：季度汇报、产品发布说明、对外提案、内部周会材料。这些场景的共同点是——内容不值得每次从零排版，但每次都要遵守同一套品牌规范。

它不适合"一次性的、追求极致视觉创意"的场合。如果你的演示需要手绘插图、复杂的动效编排、或非常规的版式构图，确定性生成器给不了你这些。它的目标是让 80% 的常规演示从"5 天"变成"半小时"，而不是取代设计师做那 20% 的精品。

理解这个边界，比理解它的功能更重要。
